## 2. Four Root Causes for Cold-Pass / Per-Calculation Micro-Overhead on Nano Server

While pure managed calculations run at identical speed across all environments and warm 10-worker native throughput on Nano Server matches Server Core, single-worker native `CoilLib` calls exhibit a small `~60–130 µs/calc` (`~2–4%`) overhead on cold runs. Technical inspection of the container image layers, [`nanoserver_sta_shim.cpp`](../../sta-shim/nanoserver_sta_shim.cpp), and [`install_sta_shim.cpp`](../../sta-shim/install_sta_shim.cpp) identifies four root causes:

### Root Cause 1: `wcifs.sys` Union-Filesystem Layer Depth (`9` Image Layers vs. `2` Layers)

- **Mechanism:** Every native `CoilLib` calculation reads its local `COI.INI` configuration and `AdaskoTheBeAsT.mdb` / `Select.dat` tables inside the container writable scratch layer (`C:\work\...` or `C:\Users\ContainerUser\AppData\Local\Temp\CoilWorkers\w_XX\`) and resolves `SysWOW64` DLLs through the Windows Container Isolation Filter driver (`wcifs.sys`).
- **Evidence:**
  - Bare `mcr.microsoft.com/windows/servercore:ltsc2025` has only **2 image layers**.
  - `adaskothebeast/nanoserver:aspnet-x86` has **9 image layers** (base Nano Server layers + copied `SysWOW64` runtime layers + `.NET` runtime layers + `install_sta_shim.exe` patch layer).
  - By comparison, `mcr.microsoft.com/dotnet/sdk:10.0-windowsservercore-ltsc2025` has **8 image layers** on top of Server Core and is actually **slower** than `adaskothebeast/nanoserver:aspnet-x86` on the 10-worker HTTP benchmark (`1,108.7 req/s` on 8-layer Server Core SDK vs. `1,206.9 req/s` on 9-layer Nano Server).
- **Impact:** Accounts for the majority of the first-pass (`Pass 1` vs. `Pass 2`) latency difference until the `wcifs.sys` filter lookup entries are warm in the kernel file cache.

### Root Cause 2: Process-Wide `CRITICAL_SECTION g_WindowLock` Contention & Linear `g_ThreadQueues` Scans

- **Mechanism:** On Server Core, `PeekMessageW`, `GetQueueStatus`, `InSendMessageEx`, and `MsgWaitForMultipleObjectsEx` read the calling thread's kernel `THREADINFO` / `CLIENTINFO` structure directly from the Thread Environment Block (`TEB` / `fs:[0x18]`) without taking a process-wide user-mode lock across all threads.
- **Evidence in [`nanoserver_sta_shim.cpp`](../../sta-shim/nanoserver_sta_shim.cpp):**
  - In `nanoserver_sta_shim.cpp`, all window and message-queue operations share a single process-wide `CRITICAL_SECTION g_WindowLock` ([`line 141`](../../sta-shim/nanoserver_sta_shim.cpp#L141)) and look up the calling thread's `ThreadMessageQueue*` by linearly scanning `std::vector<ThreadMessageQueue*> g_ThreadQueues` ([`GetOrCreateQueueLocked`, lines 284-294](../../sta-shim/nanoserver_sta_shim.cpp#L284)).
  - A single call to `Shim_PeekMessageW` ([`lines 783-793`](../../sta-shim/nanoserver_sta_shim.cpp#L783)) acquires and releases `g_WindowLock` **3 separate times**:
    1. `GetOrCreateQueue(GetCurrentThreadId())` ([`line 297`](../../sta-shim/nanoserver_sta_shim.cpp#L297))
    2. `ProcessSentMessages(queue)` ([`line 356`](../../sta-shim/nanoserver_sta_shim.cpp#L356))
    3. `TryDequeueMessage(...)` ([`line 394`](../../sta-shim/nanoserver_sta_shim.cpp#L394))
  - Similarly, `Shim_MsgWaitForMultipleObjectsEx` ([`lines 982-1012`](../../sta-shim/nanoserver_sta_shim.cpp#L982)) acquires and releases `g_WindowLock` **4 times** per call.
- **Impact:** When 10 isolated STA worker threads (`w_00`..`w_09`) pump COM/VCL messages concurrently during `CoilLib` execution, all 10 threads contend on the single `g_WindowLock` cache line.

### Root Cause 3: Uncached `IsOsShimDisabledByEnv()` (`GetEnvironmentVariableW`) and Redundant `RefreshHooksLocked()` / `VirtualProtect()` Calls

- **Mechanism:** Whenever `combase.dll`, `ole32.dll`, or `user32.dll` calls `Shim_ApiSetQueryApiSetPresence` ([`lines 1300-1312`](../../sta-shim/nanoserver_sta_shim.cpp#L1300)), `Shim_ApiSetQueryApiSetPresenceEx` ([`lines 1314-1329`](../../sta-shim/nanoserver_sta_shim.cpp#L1314)), or `Shim_ResolveDelayLoadedAPI` ([`lines 1331-1375`](../../sta-shim/nanoserver_sta_shim.cpp#L1331)), the shim checks whether it is disabled via environment variable and refreshes module hooks.
- **Evidence in [`nanoserver_sta_shim.cpp`](../../sta-shim/nanoserver_sta_shim.cpp):**
  - `IsOsShimDisabledByEnv()` ([`lines 259-268`](../../sta-shim/nanoserver_sta_shim.cpp#L259)) calls Win32 `GetEnvironmentVariableW(L"NANOSERVER_DISABLE_STA_SHIM", ...)` on every invocation (acquiring the PEB environment lock and scanning the process environment block) instead of caching the boolean in a `std::atomic<int>` updated only on `DllMain` / `NanoServerStaShim_Refresh()`.
  - Inside `Shim_ApiSetQueryApiSetPresence` and `Shim_ApiSetQueryApiSetPresenceEx`, every matching query acquires `g_HookLock` and calls `RefreshHooksLocked()` ([`lines 1574-1585`](../../sta-shim/nanoserver_sta_shim.cpp#L1574)) -> `ApplyModuleState()` ([`lines 1534-1572`](../../sta-shim/nanoserver_sta_shim.cpp#L1534)) -> `WritePointerWithProtection()` ([`lines 270-276`](../../sta-shim/nanoserver_sta_shim.cpp#L270)), which invokes two kernel `VirtualProtect` syscalls (`NtProtectVirtualMemory`, flushing TLB permissions) per IAT/delay-load slot even when `*address == value` (already patched).
- **Impact:** Adds unnecessary `NtProtectVirtualMemory` syscalls and PEB lock acquisitions whenever uncached ApiSet presence checks fire during STA thread or COM initialization.

### Root Cause 4: `KnownDLLs` Removal (`user32`, `ole32`, `gdi32`) and PE Export Forwarder Indirection

- **Mechanism:** To allow `nanoserver_sta_shim.dll` to intercept `user32.dll`, `ole32.dll`, `gdi32.dll`, and `comctl32.dll` in 32-bit WOW64 processes, [`install_sta_shim.cpp:530-546`](../../sta-shim/install_sta_shim.cpp#L530) (`RemoveKnownDllEntries`) deletes `user32`, `ole32`, and `gdi32` from `HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\KnownDLLs` and patches their PE import/export tables.
- **Evidence:**
  - Without pre-mapped kernel `KnownDLLs` section objects, when each isolated worker directory (`w_00`..`w_09`) loads its worker-local `CoilLib.dll`, `COIL.dll`, and `Selecting.dll`, the Windows loader (`ntdll!LdrpLoadDll`) must resolve dependencies via filesystem search paths and walk PE export forwarder chains (`gdi32.dll -> nanoserver_sta_shim.CopyEnhMetaFileA`, etc.) through `.edata2` rather than binding directly to pre-mapped `KnownDLLs` sections.
- **Impact:** Slightly increases one-time `LoadLibraryExW` / `GetProcAddress` cost during worker initialization and delay-load resolution.

## 3. Optional Low-Risk Micro-Optimizations for Future Releases (`v1.2.1+`)

None of these items are bugs — the current `v1.2.0` implementation is functionally complete and passes all `200 / 200` `AhuNew` tests and all `24 / 24` `nanoserver` container tests. If you ever want to shave off the remaining `~2–3%` single-worker overhead in a future `v1.2.1` update, three localized optimizations in `nanoserver_sta_shim.cpp` will eliminate Root Causes 2 and 3 completely:

1. **Skip No-Op `VirtualProtect` Calls in `WritePointerWithProtection` / `WriteInt32WithProtection` ([`lines 270-282`](../../sta-shim/nanoserver_sta_shim.cpp#L270)):**
   ```cpp
   void WritePointerWithProtection(PVOID* address, PVOID value) {
       if (*address == value) {
           return;
       }
       DWORD oldProtect = 0;
       if (VirtualProtect(address, sizeof(PVOID), PAGE_EXECUTE_READWRITE, &oldProtect)) {
           *address = value;
           VirtualProtect(address, sizeof(PVOID), oldProtect, &oldProtect);
       }
   }
   ```
2. **Store `ThreadMessageQueue*` in a Thread-Local Storage (`TlsAlloc` / `thread_local`) Slot:**
   - Fast-path `GetOrCreateQueue(GetCurrentThreadId())` by reading the thread's own `ThreadMessageQueue*` from a TLS slot without acquiring `g_WindowLock`, and add `std::atomic<bool> HasPendingMessages` on `ThreadMessageQueue` so empty-queue `Shim_PeekMessageW` and `Shim_GetQueueStatus` calls return in ~2 nanoseconds with zero lock acquisitions.
3. **Cache `IsOsShimDisabledByEnv()` When Enabled:**
   - Re-evaluate `GetEnvironmentVariableW(L"NANOSERVER_DISABLE_STA_SHIM", ...)` only during `DllMain(DLL_PROCESS_ATTACH)` and `NanoServerStaShim_Refresh()`, avoiding PEB environment scans on hot ApiSet / delay-load hooks.
