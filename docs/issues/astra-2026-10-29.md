# Astra implementation review, 2026-10-29

## Verdict

**Not everything is implemented correctly.** This review confirms **13 actionable
findings: 3 P1 and 10 P2**. The native shim builds and the new export-table patching
passes focused checks, but native behavior probes expose correctness failures
that the existing managed tests do not cover. All 24 managed test modes also
pass against the current base images; those passing tests do not negate the
independently reproduced native failures.

Reviewed the **current working tree**, including the uncommitted v1.2.0 changes,
on `main` at `d359366` (the v1.1.0 commit). This was a repository review, not only
a review of the diff. Implementation files and existing user changes were left
untouched; validation artifacts are under `.artifacts/astra-2026-10-29/`.

The ten findings in the historical
[Sol review](sol6.1-2026-10-29.md) remain applicable and were independently
revalidated. Findings 7, 11, and 13 below are additional findings. The lifecycle
finding also confirms missing destruction notifications. The blanket
production-readiness conclusion in the [Argon report](argon-2026-10-29.md) is not
supported by these results. Its external application benchmarks were not rerun.

## High-priority findings

### 1. [P1] Keep synchronous dispatch on the window's owning thread

**Location:** [`sta-shim/nanoserver_sta_shim.cpp:877-904`](../../sta-shim/nanoserver_sta_shim.cpp#L877),
with receiver-side access at [372-390](../../sta-shim/nanoserver_sta_shim.cpp#L372).

Cross-thread `SendMessageW` waits only 25 or 500 ms, then directly invokes the
target window procedure on the sender. The x64 probe returned sender thread
`1412` instead of owner `1568`; x86 returned sender `1320` instead of owner
`1668`. This violates window/STA affinity. If the receiver already dequeued the
stack-allocated `SentMessageItem` and is still executing its callback, the sender
can also dispatch a second time, close the event, and return before the receiver
writes its result, leaving a use-after-return path. Although the README describes
a same-thread-focused subset, unsupported cross-thread calls must not execute on
the wrong thread or leave dangling references.

**Fix direction:** Dispatch only on the owning thread and retain request/event
ownership until receiver completion. Remove the direct-call timeout fallback.

### 2. [P1] Stop installation when copying or patching fails

**Location:** [`sta-shim/install_sta_shim.cpp:615-622`](../../sta-shim/install_sta_shim.cpp#L615)
and [664-697](../../sta-shim/install_sta_shim.cpp#L664).

`CopyShimDll` does not report failure, every import/export-patching result is
ignored, and `wmain` returns zero unconditionally after installation. Missing
payloads or access-denied errors can therefore leave failed installation layers
marked successful. In particular, successful import patching after a failed
payload copy makes system DLLs depend on an unavailable shim. A safe
fault-injection probe against the current installer source made all 12 copies
and all 14 patch-file opens fail; the installer still returned `0`.

**Fix direction:** Validate required payloads before mutation, check each required
copy/patch operation, and return nonzero on failure. Do not continue modifying
dependent DLLs after a payload installation failure.

### 3. [P1] Deliver window creation and destruction notifications

**Location:** [`sta-shim/nanoserver_sta_shim.cpp:546-601`](../../sta-shim/nanoserver_sta_shim.cpp#L546).

`CreateWindowExW` discards `lpParam` and returns a handle without sending
`WM_NCCREATE` or `WM_CREATE`; `DestroyWindow` erases the entry without
`WM_DESTROY` or `WM_NCDESTROY`. Ordinary message-only window procedures that store
their object pointer from `CREATESTRUCT.lpCreateParams` never initialize, and
destruction-based cleanup never executes. On both architectures the probe
observed zero creation notifications instead of two, zero user context instead
of `0x123456`, and zero destruction notifications instead of four for two
windows. Server Core produced all expected notifications.

**Fix direction:** Implement the synchronous lifecycle callbacks, creation
parameters, creation-failure semantics, and destruction cleanup before removing
the window entry.

## Other confirmed findings

### 4. [P2] Restrict SetWindowLongW to four-byte writes

**Location:** [`sta-shim/nanoserver_sta_shim.cpp:727-728`](../../sta-shim/nanoserver_sta_shim.cpp#L727),
delegating to [709-715](../../sta-shim/nanoserver_sta_shim.cpp#L709).

`SetWindowLongW` delegates to the pointer-sized implementation. On x64, writing a
32-bit extra-window-data field consequently overwrites eight bytes. Setting the
field at offset 4 to `2`, then the field at offset 0 to `1`, changes the adjacent
field to `0`. The x86 implementation and Server Core control retain `2`.

**Fix direction:** Read and write `sizeof(LONG)` for the non-pointer API and retain
pointer-sized operations only for `SetWindowLongPtrW`.

### 5. [P2] Schedule callbacks for successfully created timers

**Location:** [`sta-shim/nanoserver_sta_shim.cpp:930-953`](../../sta-shim/nanoserver_sta_shim.cpp#L930).

`SetTimer` ignores the interval and callback and only returns an ID.
`SetCoalescableTimer` delegates to it, and no timer state or scheduling exists.
Code waiting for a timer message/callback never progresses despite successful
registration. A 10 ms timer with an actively pumped queue produced zero callbacks
over 150 ms on both Nano architectures; the Server Core control produced nine.

**Fix direction:** Track timers and generate due `WM_TIMER` messages/callbacks on
the owning thread; make cancellation remove the scheduled timer.

### 6. [P2] Apply wake masks and wait-all semantics before returning ready

**Location:** [`sta-shim/nanoserver_sta_shim.cpp:956-980`](../../sta-shim/nanoserver_sta_shim.cpp#L956).

The wait function ignores `dwWakeMask` and returns immediately for any queued
message, before considering the handles or `MWMO_WAITALL`. With a posted
`WM_APP` message, a `QS_SENDMESSAGE`-only wait returned `0` instead of
`WAIT_TIMEOUT (258)`. Adding an unsignaled handle and `MWMO_WAITALL` returned `1`
instead of timing out. Both failures reproduce on x86 and x64 and can turn
COM/message wait loops into premature wakeups or spinning.

**Fix direction:** Classify queued work by the requested mask and satisfy the
handle/message combination required by the wait flags before reporting success.

### 7. [P2] Block filtered GetMessage calls instead of spinning

**Location:** [`sta-shim/nanoserver_sta_shim.cpp:773-784`](../../sta-shim/nanoserver_sta_shim.cpp#L773),
with event-reset conditions at [372-379](../../sta-shim/nanoserver_sta_shim.cpp#L372).

An unmatched posted message keeps the manual-reset `WakeEvent` signaled.
`GetMessageW` cannot dequeue it because of its filter, but its 50 ms wait then
returns immediately on every iteration. A thread waiting for `WM_APP + 77` while
`WM_APP + 3` was queued consumed approximately **281 ms of CPU on x64 and 265 ms
on x86 during a 300 ms interval**; Server Core consumed zero. This is a normal
filtered-message-loop case, not a malformed-input scenario.

**Fix direction:** Wait for queue-state changes that can satisfy the filter
without repeatedly waiting on a permanently signaled any-message event or
discarding unmatched messages.

### 8. [P2] Release message queues when their owning threads exit

**Location:** [`sta-shim/nanoserver_sta_shim.cpp:301-311`](../../sta-shim/nanoserver_sta_shim.cpp#L301)
and [1693-1703](../../sta-shim/nanoserver_sta_shim.cpp#L1693).

Every new pumping thread allocates a queue and event handle. Neither is removed
when the thread exits; the DLL has no thread-detach cleanup and disables thread
notifications. Creating and joining 64 threads that each call `PeekMessageW`
leaked **64 event handles** on each architecture, versus zero in the Server Core
control. Long-lived hosts that replace workers accumulate both handles and
queue storage.

**Fix direction:** Add reliable thread-lifetime cleanup with safe handling of
pending sent messages, windows, and queue references.

### 9. [P2] Retrieve WM_QUIT regardless of the caller's filters

**Location:** [`sta-shim/nanoserver_sta_shim.cpp:416-420`](../../sta-shim/nanoserver_sta_shim.cpp#L416).

`TryDequeueMessage` applies the HWND and numeric message filters to `WM_QUIT`.
After `PostQuitMessage(17)`, a filtered `PeekMessageW` returned false on both
architectures instead of retrieving `WM_QUIT`. A filtered `GetMessageW` loop can
therefore fail to terminate during shutdown. Server Core returned the quit
message for the same call.

**Fix direction:** Exempt `WM_QUIT` from these filters and preserve its exit code
and `GetMessageW` return semantics.

### 10. [P2] Treat every nonzero test-process exit code as failure

**Location:** [`nanoserver-aspnet-x64/Tests/run_all_modes.cmd:12`](../../nanoserver-aspnet-x64/Tests/run_all_modes.cmd#L12).
The same checks occur at lines **12, 21, 30, and 39 in all six flavours'**
`Tests/run_all_modes.cmd` files.

`if errorlevel 1` misses negative Windows crash statuses, such as access
violation `0xC0000005` / `-1073741819`. A fresh isolated reproduction made all
four test invocations return that status; the runner continued, printed
`ALL 4 MODES PASSED SUCCESSFULLY!`, and returned zero. Positive exit `1`
correctly stopped at the first mode, demonstrating the signed-status gap.

**Fix direction:** Check for any nonzero status immediately after each invocation,
for example `if not "%errorlevel%"=="0" exit /b %errorlevel%`.

### 11. [P2] Propagate each DISM capability-installation failure

**Locations:** Lines **4-7 and 14-24** in:

- [`nanoserver-iis-aspnet-x64/install_features.cmd`](../../nanoserver-iis-aspnet-x64/install_features.cmd#L4)
- [`nanoserver-iis-aspnet-x86/install_features.cmd`](../../nanoserver-iis-aspnet-x86/install_features.cmd#L4)
- [`nanoserver-iis-netfx-x64/install_features.cmd`](../../nanoserver-iis-netfx-x64/install_features.cmd#L4)
- [`nanoserver-iis-netfx-x86/install_features.cmd`](../../nanoserver-iis-netfx-x86/install_features.cmd#L4)

The main script ignores both `:AddCap` results and unconditionally returns zero.
Its subroutine also treats every positive status at least `3010` as reboot
success and misses negative failures. Mocked DISM exits `87`, `3011`, and
`-2146498529` all produced script exit `0` in all four variants. A failed
servicing step can consequently become a successful cached Docker layer, even
if a later build step detects the missing feature. The non-IIS x86 capability
script correctly propagated the same failures.

**Fix direction:** Accept only `0` and `3010` as successful DISM results and
propagate every other result immediately after each capability call.

### 12. [P2] Remove the native exit-code check after version updates

**Location:** [`push.ps1:20-21`](../../push.ps1#L20).

In a fresh PowerShell session, `push.ps1 -Version 1.2.0` runs
`set-version.ps1`, rewrites the six flavour scripts, and then fails under strict
mode because `$LASTEXITCODE` has never been set. The version updater runs no
native executable. A stale nonzero native status can also cause a false
failure. This was reproduced on an isolated repository snapshot with Docker
mocked; publication was never reached.

**Fix direction:** Rely on terminating PowerShell errors or an explicit return
contract from the version updater, not unrelated native process status.

### 13. [P2] Tie the IIS container lifetime to service availability

**Locations:**

- [`nanoserver-iis-aspnet-x64/Dockerfile:85`](../../nanoserver-iis-aspnet-x64/Dockerfile#L85)
- [`nanoserver-iis-aspnet-x86/Dockerfile:87`](../../nanoserver-iis-aspnet-x86/Dockerfile#L87)
- [`nanoserver-iis-netfx-x64/Dockerfile:71`](../../nanoserver-iis-netfx-x64/Dockerfile#L71)
- [`nanoserver-iis-netfx-x86/Dockerfile:71`](../../nanoserver-iis-netfx-x86/Dockerfile#L71)

The startup command suppresses W3SVC startup diagnostics and unconditionally
continues into `ping -t`, even when `net start w3svc` fails. For example, invalid
IIS configuration can prevent its WAS dependency from starting while the
container remains running without a web server. The exact startup command,
tested with isolated executable mocks, ran ping after `net.exe` returned `2`.
Later service termination also does not terminate the container, so exit-based
restart policies do not recover it.

**Fix direction:** Preserve startup errors, return failure when startup fails,
and use a foreground service monitor that exits when the required IIS services
stop.

## Coverage and limitations

- Reviewed the native shim, export definition, installer, build script, all six
  base Dockerfiles, installation scripts, root/per-flavour tooling, both ANCM
  registration copies, sample projects, test runners, and all unique available
  C# tests/helpers. Duplicate variants were compared rather than assumed equal.
- **None of the six `Tests` trees contains the `src` directory claimed by
  [`README.md:90`](../../README.md#L90).** The test projects reference NuGet
  `AdaskoTheBeAsT.Interop.COM` 4.2.0 instead. Consequently, the managed COM
  library, ATL server, and native lifetime probe implementation sources were
  not available here for an internal code audit.
- Existing tests do not establish full native Win32 parity. For example,
  [`NanoServerWindowManagerTest.cs:354-370`](../../nanoserver-aspnet-x64/Tests/AdaskoTheBeAsT.Interop.COM.Test/NanoServerWindowManagerTest.cs#L354)
  expects timeout-based direct cross-thread dispatch; timer assertions at
  [412-417](../../nanoserver-aspnet-x64/Tests/AdaskoTheBeAsT.Interop.COM.Test/NanoServerWindowManagerTest.cs#L412)
  check IDs/cancellation, not delivery; the wait assertion at
  [425-426](../../nanoserver-aspnet-x64/Tests/AdaskoTheBeAsT.Interop.COM.Test/NanoServerWindowManagerTest.cs#L425)
  expects message readiness with a zero wake mask. These call the managed
  implementation directly. Mode 4 runs only one state-toggle test.
- The new GDI/control exports are deliberately documented as minimal headless
  compatibility stubs. Missing full rendering is not counted as a bug here;
  the fixture checks do not establish complete GDI/control behavior.
- No clean base-image rebuild, external application's 200-test suite,
  performance benchmark, live IIS health request, or image publication was
  performed. Current-base testing reused compiled test payloads and does not
  establish a clean source rebuild or low-privilege compatibility. This review
  is not an exhaustive proof of every workload or API.
