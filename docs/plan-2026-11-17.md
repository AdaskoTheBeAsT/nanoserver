## Detailed technical plan

### NS-10 (P0): Diagnose and fix WoW64 x86 `STATUS_CONFLICTING_ADDRESSES` (`0xC0000018`) on `nanoserver-iis-aspnet-x64`

#### Evidence
In [`docs/plan-2026-11-14.md`](plan-2026-11-14.md) (`Remaining startup blocker`), two fresh-container WoW64 x86 runs on `nanoserver-iis-aspnet-x64` (`native-atomic-iis-aspnet-x64-x86` and `api-atomic-iis-aspnet-x64-x86`) exited before main probe output with `0xC0000018` (`STATUS_CONFLICTING_ADDRESSES`), without ASLR/NX/CFG relaxation.

#### Design
1. Inspect preferred `ImageBase`, `.reloc` stripping/presence, section alignment, and WoW64 system DLL/shim/rewritten-forwarder base-address ranges across all 32-bit payloads installed into `C:\Windows\SysWOW64` (`nanoserver_sta_shim_x86.dll`, `olepro32.dll`, promoted/rewritten `SysWOW64` forwarder DLLs, and `NativeShimRegression_x86.exe`) on `nanoserver-iis-aspnet-x64` vs `nanoserver-aspnet-x64` and `nanoserver-iis-netfx-x64`.
2. Ensure every synthesized or rewritten PE32 DLL in `SysWOW64` preserves a valid base-relocation directory (`IMAGE_DIRECTORY_ENTRY_BASERELOC`, `/DYNAMICBASE` without stripping `.reloc` during import/export table preparation in `install_sta_shim.cpp`) and uses non-colliding default `ImageBase` ranges outside WoW64 reserved thunks (`ntdll` / `wow64` / `wow64win` / `wow64cpu` / `kernel32` / `user32`).
3. Capture deterministic before/after PE header & WoW64 virtual-address-map evidence inside disposable containers; never accept retry-until-green without an established loader mechanism fix.

#### Acceptance
- Root cause of `0xC0000018` is proven with concrete PE/VA evidence, fixed without disabling `/DYNAMICBASE`, `/NXCOMPAT`, or `/GUARD:CF`, and verified across at least **64/64** consecutive fresh-process WoW64 x86 launches on `nanoserver-iis-aspnet-x64` plus the full 6-flavour native/API/IIS/mapped-installer matrix.

### NS-11 (P1): Non-mutating `SysWOW64\odbccp32.dll` stub companion for legacy VB6 / DAO / OLE DB binaries

#### Evidence
Legacy 32-bit Visual Basic 6 and DAO/Jet calculation DLLs frequently contain static imports or `Declare Function SQLConfigDataSource Lib "ODBCCP32.DLL"` bindings. On Windows Nano Server 2025, `SysWOW64\odbccp32.dll` is absent, causing `LoadLibraryExW` or VB6 `DllFunctionCall` resolution to fail with `ERROR_MOD_NOT_FOUND (126)` unless each consumer binary-patches its own DLL image.

#### Design
1. Add a minimal CRT-free, entrypoint-free (or no-op `DllMain` with CFG/ASLR/NX) `odbccp32.dll` (`x86` and `x64` parity) built in `sta-shim/build_shim.ps1` and installed only when absent in `SysWOW64` / `System32` (never overwriting an existing OS DLL).
2. Export honest, non-mutating stubs matching the Windows `odbccp32.dll` `stdcall` ABI and ordinals:
   - `SQLConfigDataSource` / `SQLConfigDataSourceW`: never touches `HKCU\Software\ODBC` or `HKLM\SOFTWARE\ODBC`; records thread-local installer error `ODBC_ERROR_REQUEST_FAILED` (`11`) and returns `FALSE` (`0`).
   - `SQLInstallerError` / `SQLInstallerErrorW`: reports the recorded installer error code/message cleanly with bounded buffer writes and returns `SQL_NO_DATA` (`100`) when empty.
3. Synchronize SHA-256 payload hashes across all six image contexts and add `NativeShimRegression` coverage.

#### Acceptance
- `LoadLibraryExW("odbccp32.dll", ...)` and `GetProcAddress` succeed under `ContainerUser` on x86 and x64 Nano Server images, `SQLConfigDataSource` returns `FALSE` without creating any `Software\ODBC` registry keys, and `SQLInstallerError` respects output buffer bounds.

### NS-12 (P1): Upgrade 6-flavour four-mode managed test matrix to `AdaskoTheBeAsT.Interop.COM` `5.0.0`

#### Evidence
`docs/plan-2026-11-14.md` notes that the existing container test projects (`nanoserver-*/Tests`) reference packaged `AdaskoTheBeAsT.Interop.COM` `4.2.0`, so `COM-01`–`COM-17` (including `NS-09` capability-bit handoff between `nanoserver_sta_shim` `1.8.0` and `NanoServerOle2Shim` / `NanoServerDispenserManager`) have not yet been exercised inside live `1.8.0` candidate containers.

#### Design
1. Feed locally packed `AdaskoTheBeAsT.Interop.COM` `5.0.0` (and matching `5.0.0` `Interop.Threading` / `Interop.Unmanaged` test packages where applicable) into a local container test feed for `nanoserver-*/Tests` without publishing to NuGet.org.
2. Add container regression tests across all four provider modes (`OS shim active`, `OS shim disabled + managed fallback`, `ForceInProcessFallback`, and `capability bit handoff`):
   - Verify `NanoServerStaShim_GetCapabilities` causes `NanoServerOle2Shim` and `NanoServerDispenserManager` to defer cleanly to the OS shim in `1.8.0` and activate cleanly when OS shim bits are masked/absent (`1.7.0` control image).
   - Verify `IComActivationScope` + `UnloadModulesOnDeactivate = true` unmaps worker COM DLLs and deletes temporary worker directories inside `ContainerUser`.
   - Verify `ComClassFactory`, `ComErrorDiagnostics` (`IErrorInfo`), `ComModuleDiagnostics.VerifyRegisteredInprocServer`, `SafeArrayMarshal`, `CurrentUserRegistryLeaseManager` (forward & reverse `ProgIDFromCLSID`), `NanoServerOle2Shim.SuppressUninitializeImports`, and `ComAutomationLocaleScope`.

#### Acceptance
- All 6 Nano Server candidate flavours (`aspnet-x86`, `aspnet-x64`, `iis-aspnet-x86`, `iis-aspnet-x64`, `iis-netfx-x86`, `iis-netfx-x64`) + `1.7.0` backward-compatibility control pass 100% of the four-mode `Interop.COM` `5.0.0` container test matrix with `0` skipped or retried failures.
